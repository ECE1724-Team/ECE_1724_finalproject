# Authentication and Authorization Implementation

This guide describes the backend implementation on `feat/authentication`. Requirements come from the existing PRD, API contract and database design. The original document bodies are retained; this guide records concrete implementation choices and the requester's later configuration confirmations dated 2026-11-11.

## Runtime and dependencies

Use the project's existing Express, TypeScript, PostgreSQL/`pg`, `node-pg-migrate` and Better Auth stack. Better Auth and its core adapter API are pinned together at 1.7.20. Nodemailer provides provider-independent SMTP, `jose` verifies the library-compatible verification JWT, and `cors` handles exact-origin browser credentials. `tsx` and type definitions are development dependencies. No ORM, alternate password library, admin roles or AI-provider dependency is introduced.

The backend is ESM because Better Auth's Express integration requires it. Package/lock files record exact added dependency versions. Password hashing, verification, Session cookies and native reset consumption remain Better Auth responsibilities.

## Shared identity and schema handoff

| Item | Implemented contract |
|---|---|
| Database | Same PostgreSQL database as the future business tables |
| Authoritative user key | `public.auth_user.id UUID`, generated by PostgreSQL |
| Native core tables | `auth_user`, `auth_account`, `auth_session`, `auth_verification`; default Better Auth camelCase columns |
| Business owner IDs | UUID FKs to `auth_user(id)`; define lifecycle/FK actions with the business owner |
| API/TypeScript IDs | Opaque strings; database UUID storage is not a permission check |
| Trusted context | `res.locals.auth = { userId, sessionId, emailVerified: true }` |
| Session representation | An opaque library-managed Session cookie, not a project-issued JWT |

The adapter's SQL identifiers come from the reviewed schema and a fixed auth-model allowlist; values are bound parameters. Application, resume, workspace and conversation ownership checks use the trusted context and fixed parameterized queries. Cross-user and nonexistent business resources both return 404. Invalid or unverified Sessions cannot create trusted context.

The auth migrations precede business FKs in the shared `node-pg-migrate` history. No business tables or competing auth schema are created here. Keep the existing business/AI migration dependencies, including the message/run mutual-FK ordering, under the business database owner's control.

## HTTP integration

The project exposes the documented `/api/auth` signup, signin, signout, get-session, verification send/callback, reset request/callback/submission, password change, profile update, Session list and single-Session revocation routes. Other library endpoints are not exposed implicitly. The optional Bearer plugin is not enabled; browser clients use cookies.

Mount the project auth handler before `express.json()` so the library receives the original stream. Origin/CSRF checks stay enabled, and provided origins/callbacks must match the configured trust boundary. The Express integration overwrites the internal client-IP header from its configured proxy-aware address; callers cannot supply that identity themselves. CORS permits only exact configured origins with credentials.

Registration returns `token: null` without a login Session. Correct passwords do not let unverified users sign in. First successful verification persists the verified state and establishes a Session; the frontend then reads get-session. JSON verification may still return `user: null`. Trusted callbacks retain the documented redirects; untrusted callbacks are rejected without redirecting to them.

The reset-link GET checks only and redirects; it never consumes, renews, changes a password or revokes Sessions. The submission repeats latest/expiry/unused checks. A successful reset consumes its native record, changes the password and revokes every old Session in one transaction. It creates no new login Session.

For an authenticated request to revoke another user's Session, Better Auth returns a generic success without deleting that Session. List/revocation remain ownership-scoped; the generic response is not proof that the supplied token existed.

## Credential replacement and SMTP acceptance

The requester selected a seven-day Session, 60-second same-recipient/purpose email cooldown, five requests per 900-second window, and activation only after SMTP acceptance. The 900-second credential lifetime is independent of the Session lifetime.

`auth_credential_state` has one row per `(user_id, purpose)`. A monotonically increasing `sequence` reserves each send attempt. The nullable `active_sequence`, current issuance ID/digest and expiry group describe the accepted current link. Reserving a send changes no active fields. A fresh random verification JWT nonce distinguishes same-second sends. Native reset records retain the library's generic identifier/value semantics.

After the account transaction commits, the in-process mail queue sends the prepared message outside database locks. Successful SMTP acceptance triggers a new short activation transaction. Only a higher accepted sequence may replace the current link, so a slower older send cannot restore an obsolete credential after a newer accepted send. Failed/rejected sends leave the old active link unchanged. An expired prepared credential is not activated. The HTTP generic acceptance response does not disclose whether mail was sent.

`auth_email_rate_limit` applies the confirmed limits to existing and unknown recipients using HMAC keys, without storing additional plaintext email addresses there. Limits count requests, including failed send attempts. Better Auth's native IP/path limiter uses an independent PostgreSQL pool and atomic custom storage, so failed account transactions do not roll back security counters. Raw paths/tokens are hashed before storage.

SMTP acceptance and database activation are separate systems. A process/storage failure after acceptance may leave that prepared link inactive; it does not authorize restoring an obsolete link or bypassing the current-state check. Errors are reported with safe codes, and users can request another email. The implementation does not claim durable mail replay, automatic cross-system recovery or inbox-delivery guarantees.

## Atomicity and cache behavior

The project `Database` uses its own AsyncLocalStorage to share one PoolClient across the HTTP wrapper, native Better Auth operations and credential checks. Nested adapter transactions join it; a nested/query failure makes the transaction rollback-only even if the library catches the exception. A success response/cookie is forwarded only after the outer commit succeeds.

Signin, verification and reset use the same user lock ordering. This prevents an old-password signin from creating a Session after a concurrent reset has revoked Sessions. Latest-credential checks remain inside that transaction; reset GET approval is never reused as POST authorization. Single-row native consumption is an atomic `DELETE ... RETURNING` operation.

Cookie caching is disabled. Session reads used by business authorization bypass cached data and do not refresh the Session. The regular get-session HTTP endpoint retains the library's refresh behavior and cookie handling. Revoked Session rows cannot be recreated by a stale cookie. Never cache the trusted user context across requests.

## Frontend and teammate checklist

- Set the frontend's exact origin in `AUTH_TRUSTED_ORIGINS`; send credentialed requests and use trusted callback URLs.
- Render registration waiting/resend states. Treat generic send acceptance as account-neutral, and respect 429/Retry-After.
- Query get-session after first verification; use the resulting verified identity rather than the verification JSON `user` field.
- After reset success, navigate to sign-in. Treat every old Session as revoked.
- Rongxin can now use UUID owner FKs to `auth_user(id)` after the auth migrations. Business handlers still check usability and owner-scoped lifecycle rules.
- Jianye and other backend contributors mount resource operations behind the shared verified-session middleware and the appropriate ownership middleware.

See [backend startup and checks](../backend/README.md). Tests use isolated PostgreSQL databases, local SMTP and no external mail credentials. A real SMTP provider and the team's actual development database must be configured separately before a live end-to-end email demonstration.
